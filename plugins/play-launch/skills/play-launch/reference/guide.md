# 구글 플레이 앱 등록 가이드 — 시행착오를 줄이기 위한 것

> 작성 2026-11-17 · 개정 2026-11-23
> 근거: 출시 2회 — ① 사례 A(일반 앱): React Native(Expo) 앱 첫 출시(출시 기록 문서를 남김)
> ② 사례 B(게임 앱): 가로형 Capacitor(WebView) 게임 첫 출시(광고 포함, Play 밖 배포 이력 없음)
>
> 이 문서는 **실제로 끝까지 가 본 경험**을 다른 프로젝트에 쓸 수 있게
> 일반화한 것이다. 앱 둘, 계정 둘 이하의 경험이라는 한계가 있다.
>
> - **[확인]**: 실제 화면이나 빌드 결과로 확인한 사실
> - **[이 계정]**: 이 계정에서는 그랬지만 계정마다 다를 수 있는 것
> - **[문서]**: 구글 도움말 원문 기준
> - **[가설]**: 한 번 겪었거나 추정한 것. 단정해서 안내하지 않는다
> - **[문서 확인 필요]**: 공식 기준을 확인하지 못한 것. 안내 전에 도움말을 찾아 원문을 인용한다
>
> 콘솔 화면은 자주 바뀐다. **이 문서를 정답표로 쓰지 말고, 화면과 대조하는
> 체크리스트로 쓴다.**

## 0. 진행 원칙 — 가장 중요하다

이번 출시에서 생긴 오류는 대부분 **화면이나 코드를 확인하기 전에 답한 것**에서
나왔다. 그래서 진행 방식을 다음과 같이 고정한다.

1. 사용자가 콘솔 화면을 캡처한다
2. **그 화면에 보이는 항목 하나**에 대해서만 입력값과 근거를 말한다
3. 사용자가 입력하고 다음 화면을 캡처한다

- **다음 단계를 미리 말하지 않는다.** 화면에 없는 메뉴 경로를 기억으로 안내하지 않는다
- 선택지가 있는 항목(태그, 설문)은 **화면에 실제로 나온 목록**에서만 고른다
- 답의 근거가 앱 동작이면 **코드를 열어 확인한 뒤** 답한다
- 예견되는 오류(예: 버전 코드)는 **나면 대응하지 말고 미리 처리한다**
- 사용자가 이미 답한 것(예: 키스토어 백업)은 다시 묻지 않는다

## 1. 콘솔에 들어가기 전에 — 빌드·자산 사전 점검

이번에 콘솔에서 막힌 두 가지(16KB, 버전 코드)와 스크린샷 문제는 모두 **미리
점검할 수 있었다.** 콘솔을 열기 전에 아래 항목을 끝낸다.

### 1-1. 버전 코드

- **[확인]** 한 번 업로드한 AAB의 버전 코드는 출시하지 않고 지워도 **다시 쓸 수 없다**
- 따라서 AAB를 교체할 일이 생기면 **업로드 전에 버전 코드를 먼저 올린다**
- Expo prebuild 프로젝트는 `android/` 가 다시 만들어지므로 `app.json` 의
  `android.versionCode` 에도 넣어야 값이 유지된다
- **[확인]** 버전 코드가 적힌 곳은 프로젝트마다 다르다. `app.json` 이나 `applicationId`
  근처만 보지 말고, `android/app/build.gradle` 의 `versionCode` 가 **무엇을 읽는지**
  끝까지 따라간다. Capacitor·직접 관리하는 gradle 프로젝트에서는 `versionCode` 가
  사용자 정의 변수(예: `ext` 블록이나 파일 상단의 `def xxxVersionCode = N`)를 읽는 경우가 있었다
- `versionName` 도 마찬가지다. 다른 설정 파일(예: 프로젝트 메타데이터 JSON)에서 읽어 오는
  경우가 있으니 출처를 한 번 확인한다

### 1-2. 16KB 메모리 페이지 정렬

- **[확인]** 64비트 `.so` 중 하나라도 4KB 정렬이면 프로덕션 버전 저장이 막힌다
  ("앱이 16KB 메모리 페이지 크기를 지원하지 않습니다")
- 미리 만들어진 라이브러리는 보통 이미 16KB이다. 문제는 **우리 빌드에서 직접 컴파일되는
  네이티브 모듈**이다. 사례 A에서는 `onnxruntime-react-native` 의 JSI 라이브러리가
  여기에 해당했다. NDK r27의 기본 정렬은 4KB이다
- 해결 방법은 해당 CMake 타깃에 `-Wl,-z,max-page-size=16384` 를 추가하는 것이다. 수정이
  `npm install` 뒤에도 남도록 postinstall 패치로 넣는다
- `무시하고 계속하기` 는 쓰지 않는다. 16KB 페이지 기기에서 시작하자마자 죽을 수 있다

**검사 방법.** AAB를 zip으로 풀고, `base/lib/arm64-v8a/`·`base/lib/x86_64/` 의
`.so` 마다 ELF 프로그램 헤더 중 `PT_LOAD` 의 `p_align` 이 16384 이상인지 본다.

```js
// check16k.mjs — 사용법: node check16k.mjs <풀어 둔 AAB 폴더>
import fs from 'node:fs';
import path from 'node:path';
const walk = d => fs.readdirSync(d, { withFileTypes: true }).flatMap(e =>
  e.isDirectory() ? walk(path.join(d, e.name)) : [path.join(d, e.name)]);
for (const f of walk(process.argv[2]).filter(f => f.endsWith('.so'))) {
  const b = fs.readFileSync(f);
  if (b[4] !== 2) continue;                       // ELF64만 (32비트는 대상 아님)
  const phoff = Number(b.readBigUInt64LE(0x20));
  const phentsize = b.readUInt16LE(0x36), phnum = b.readUInt16LE(0x38);
  let min = Infinity;
  for (let i = 0; i < phnum; i++) {
    const o = phoff + i * phentsize;
    if (b.readUInt32LE(o) === 1)                  // PT_LOAD
      min = Math.min(min, Number(b.readBigUInt64LE(o + 0x30)));
  }
  console.log(min >= 16384 ? 'OK  ' : 'FAIL', min, path.relative(process.argv[2], f));
}
```

AAB를 푸는 방법: 파일을 `.zip` 으로 복사한 뒤 `Expand-Archive` 로 푼다.
AAB를 풀지 않고 빌드 중간 산출물 `android/app/build/intermediates/stripped_native_libs`
폴더에 바로 돌려도 된다. 사례 A에서 수정 후 빌드에 돌려 64비트 `.so` 29개가 모두
`OK 16384` 로 나오는 것을 확인했다. 실패(4KB) 사례에는 이 스크립트를 돌려 보지 않았다.
당시에는 같은 원리의 다른 스크립트로 `libonnxruntimejsi.so` 를 찾아냈다.

**결과가 한 줄도 안 나올 때.** 스크립트는 `.so` 만 검사하므로, 앱에 네이티브 라이브러리가
없으면 아무것도 출력하지 않는다.

- 먼저 **경로가 맞는지** 확인한다. `base/lib/` 폴더 자체가 있는지, 압축을 제대로 풀었는지 본다
- 경로가 맞고 `lib/` 가 없거나 비어 있으면 **이 검사는 해당 없음**이다.
  **[확인]** WebView 기반 앱(Capacitor 등)은 플러그인이 Java/Kotlin뿐이면 `.so` 가 0개였다
- 광고·분석 SDK를 붙이면 `.so` 가 생길 수 있으므로 **SDK를 더할 때마다 다시 돌린다** [가설]

### 1-3. 스크린샷

- **[확인]** 업로드 화면 조건은 **가로세로 비율 16:9 또는 9:16**이다. 한 변은 320~3840px,
  24비트(알파 채널 없음), 장당 8MB 이하
- 요즘 폰 원본(예: 1080×2220, 약 9:18.5)은 **그대로 올라가지 않는다.** 상태 표시줄과
  내비게이션 바를 잘라 1080×1920으로 맞춘다. 화면마다 내용이 잘리지 않도록
  자르는 위치를 따로 정한다
- 최소 2장, 최대 8장이다
- **[확인]** 업로드하면 순서가 섞인다. 올린 뒤 끌어서 순서를 맞춘다
- 광고가 있는 화면은 네트워크를 끊고 찍는다. USB adb는 `adb shell svc wifi disable`·
  `svc data disable` 로 끊어도 연결이 유지된다
  (`settings put global airplane_mode_on 1` 은 값만 바뀌고 실제로는 안 꺼진다)
- `adb exec-out screencap -p > x.png` 는 PowerShell에서 PNG를 깨뜨린다. 기기에
  저장한 뒤 `pull` 한다

**가로형 앱(게임 등).** 16:9 가로 스크린샷이 필요하다.

- **[확인]** 실기기 캡처를 잘라 맞추는 것보다, 앱을 PC 브라우저·에디터·개발용 미리보기에서
  **16:9 창 크기**(예: 1920×1080)로 띄워 캡처하는 편이 빨랐다
- 이 경우에도 화면 내용은 **실제 앱 화면**이어야 한다. 개발용 표시(디버그 메뉴, 개발판임을 알리는 버전 꼬리표
  등)가 찍히지 않았는지 본다

**이미지 생성 AI로 꾸밀 때.**

- **[확인]** 이미지 생성 AI(예: Gemini)에 캡처를 넣고 꾸며 달라고 하면 **화면 자체를 다시 그려**
  UI 글자·버튼·배치가 바뀌었다. 바뀐 결과를 그대로 올리면 실제 앱과 다른 화면을 보여 주게 된다.
  **원본 캡처와 나란히 놓고 UI가 그대로인지** 대조한다. 테두리·배경·문구를 덧입히는 용도로만 쓴다

**크기·형식 변환.**

- ImageMagick이 없으면 Python PIL(Pillow)로 해도 된다. 크기 조정과 함께
  **알파 채널을 없애 24비트 RGB로 저장**한다(`Image.convert('RGB')`).
  변환 뒤 크기·모드를 다시 읽어 확인한다

### 1-4. 그 밖의 자산

| 항목 | 조건 |
|---|---|
| 앱 아이콘 | 512×512, 32비트 PNG(알파 가능), 1MB 이하 |
| 그래픽 이미지 | 1024×500, JPEG 또는 24비트 PNG(알파 없음) |
| 개인정보처리방침 | **접속되는 URL**. 광고 SDK를 쓰면 광고 ID 수집을 적어 둔다 |
| 개발자 웹사이트 | 광고 앱은 **필수로 취급한다.** 이 도메인 루트에 `app-ads.txt` 를 올려 둔다 (§3) |

### 1-5. 등록정보 문안

- **[확인]** 예전에 써 둔 문안에 앱 실제 동작과 다른 서술이 3곳 있었다
- 설명문에 적은 기능과 예시는 **하나하나 코드와 대조**한 뒤 붙여 넣는다
  (화면에 실제로 보이는 항목, 실제 데이터에 있는 단어인지)

### 1-6. 광고가 있는 앱

- 릴리스 빌드에 **실제** 앱 ID와 광고 단위 ID가 들어갔는지 확인한다. 테스트 ID
  `ca-app-pub-3940256099942544` 가 남아 있으면 안 된다
- 매니페스트에 `com.google.android.gms.permission.AD_ID` 가 들어갔는지 확인한다
  (`aapt2 dump permissions`). 데이터 보안·광고 ID 선언의 근거가 된다
- **자기 앱의 실제 광고는 절대 누르지 않는다.** 무효 클릭으로 계정이 정지될 수 있다

### 1-7. 서명

- 업로드 키스토어와 비밀번호는 콘솔 작업 전에 백업한다. 잃어버리면 업데이트를 올릴 수 없다

**Play 앱 서명 — 처음 한 번만 정해지는 것.**

- **[이 계정]** 새 앱에서 콘솔은 서명 방식을 따로 묻지 않고 **Google이 생성한 앱 서명 키(기본값)**로
  진행했다. 처음 업로드한 AAB에 서명한 키가 **업로드 키**로 등록된다
- 「자체 앱 서명 키 제공」이 의미 있는 경우는 하나다 — **Play 밖에서 같은 키로 서명한 APK가
  이미 사용자 기기에 깔려 있고, 그 설치본을 Play 판으로 덮어 업데이트하게 하려는 경우.**
  그렇지 않으면 기본값으로 둔다
- **이 판단의 전제를 먼저 사용자에게 묻는다:** "Play 밖(웹사이트·배포 사이트·직접 전달)으로
  배포해서 **실제로 다른 사람 기기에 설치된** APK가 있습니까?" 기록 문서나 계획 문서에
  「○○에 배포」라고 적혀 있어도 **실제로 배포됐는지는 사용자 답으로 확인한다**
- [문서 확인 필요] 앱 서명 방식을 첫 출시 뒤에 바꿀 수 있는지, 어떤 조건에서 가능한지

**기본값(Google 생성 키)으로 간 뒤에 생기는 일.**

- **[확인]** Play 설치본은 Google의 앱 서명 키로 서명되므로, **직접 서명한 APK를 그 위에 덮어 깔 수 없다**
  (서명 불일치). 반대 방향도 같다
- 그래서 개발용 폰에 직접 서명 APK가 깔려 있으면 Play 판으로 옮길 때 **삭제 후 재설치**를 해야 한다.
  앱 데이터가 로컬에만 있으면(세이브 등) **지우기 전에 내보내기**를 하고, Play 판 설치 뒤 가져와야 한다.
  내보내기 기능이 없으면 이 단계 전에 만들어 둔다
- 이후 개발 중 확인은 내부 테스트 트랙(또는 Play 판과 따로 설치되는 디버그 빌드)으로 한다 [가설]

### 1-8. WebView 앱이 웹 내용물을 원격으로 바꾸는 경우 (해당할 때만)

Capacitor·Cordova 등에서 업데이터 플러그인으로 HTML/JS 묶음을 받아 갈아 끼우는(OTA) 앱이 대상이다.

- [가설] WebView 안에서 도는 HTML/JS만 바꾸는 것은 Play 정책이 허용하는 범위로 해석했다.
  **네이티브 쪽(플러그인 추가·판올림, 매니페스트, 권한, Java/Kotlin 코드) 변경은 반드시 새 AAB로**
  심사를 거쳐 낸다
- [문서 확인 필요] 근거 정책(기기 및 네트워크 악용 정책의 「다른 출처에서 실행 코드를 내려받는 것」
  관련 조항)의 현재 원문. 해석에 기대어 안내하지 말고 원문을 인용한다
- 원격으로 바꾼 내용도 **등록정보·데이터 보안 신고와 어긋나면 안 된다.** 새 SDK·새 수집이
  생기는 변경은 OTA가 아니라 새 버전 + 신고 수정으로 한다 [가설]
- 업데이터가 외부 서버로 통계를 보내는 설정이 기본으로 켜져 있으면 데이터 보안 신고 대상이
  될 수 있다. 끄거나 신고에 넣는다 [가설]

## 2. 콘솔 진행 순서

이번에 실제로 지나간 순서다. 각 단계는 **화면을 캡처해 대조하면서** 진행한다.

### 2-1. 대시보드 할 일 목록 → 앱 설정

- **[확인]** 앱을 만들면 대시보드에 할 일 목록이 나온다. 메뉴를 찾아 들어갈 필요 없이
  **목록 항목을 바로 누르면 된다**
- **[이 계정]** 처음에는 출시 트랙이 내부 테스트만 열려 있다. 앱 설정을 마치니
  프로덕션까지 열렸고, `프로덕션 신청`(테스터 12명·14일) 요건은 **나오지 않았다.**
  계정 종류와 생성 시기에 따라 다를 수 있으니 대시보드를 보고 판단한다
- **[이 계정]** 두 번째 출시에서도 이 요건이 나오지 않았다(오래된 개인 계정).
  일정을 짤 때는 **계정 생성일**(등록비 결제 내역 등)을 미리 확인해 두면 예상에 도움이 된다.
  [문서 확인 필요] 요건이 적용되는 계정 생성 기준일. 기준일을 안내할 때는 도움말 원문을 인용한다.
  **최종 판단은 여전히 대시보드다**
- **[가설 — 미검증]** 비공개 테스트 → `프로덕션 신청` 단계는 이 가이드의 출시 2회에서 **한 번도 겪지 않았다.**
  두 계정 모두 요건이 적용되지 않는 계정이었다. 그래서 이 단계의 진행 방법·화면·걸림돌은 이 문서에 없다.
  [문서] 도움말 「새로운 개인 개발자 계정의 앱 테스트 요구사항」 기준: 2023년 11월 13일 이후 만든
  개인 계정은 테스터 12명 이상이 14일 이상 연속 참여한 비공개 테스트를 거쳐야 프로덕션 액세스를 신청할 수 있다
  (https://support.google.com/googleplay/android-developer/answer/14151465?hl=ko).
  이 단계가 대시보드에 보이면 **도움말 원문과 그 화면을 기준으로** 진행하고, 진행할 때마다 원문을 다시 열어 수치를 대조한다

| 항목 | 답을 정하는 근거 |
|---|---|
| 개인정보처리방침 | 1-4의 URL |
| 앱 액세스 권한 | 로그인 없이 모든 기능을 쓸 수 있는지 |
| 광고 | 광고 SDK가 있는지 |
| 콘텐츠 등급 | **설문 화면을 캡처해 문항마다** 앱 내용으로 답한다 |
| 타겟층 | 실제로 정한 대상 연령 |
| 데이터 보안 | **코드 근거**: 앱의 네트워크 호출 여부, 저장 위치, SDK가 수집하는 것 |
| 정부·금융·건강 | 해당 여부 |

> 콘텐츠 등급과 데이터 보안은 이번에 **기억으로 안내했다가 틀렸다.** 어느 문항인지는
> 기록이 남지 않았다. 이 두 화면은 반드시 문항을 보면서 답한다.

**콘텐츠 등급 설문 — 답은 콘텐츠를 세어서 정한다.**

- 이야기·대사가 많은 앱(게임 등)은 「폭력·피·음주·약물·욕설·도박」 문항마다 **실제 데이터(대사 파일,
  문자열 리소스)를 검색해 횟수와 예시를 세어** 근거로 붙인다. 기억이나 인상으로 답하지 않는다
- **[확인]** 등급 결과가 **「15세 이상 · 약물」**로 나왔다
- **[가설]** 「약물」 사유는 대사 속 술 언급 때문인 것으로 추정했다. 원인을 확인하지는 않았다.
  한국 등급 체계의 「약물」 표시가 술·담배 언급을 함께 묶는지도 추정이다
  ([문서 확인 필요] 등급 기관별 표시어의 정의)
- 등급 표시를 바꾸고 싶으면 **콘텐츠를 먼저 고친 뒤** 설문을 다시 제출한다.
  콘텐츠는 그대로 두고 설문 답만 바꾸는 것은 허위 신고다

**데이터 보안 — 광고 SDK만 쓰는 앱(자체 서버·로그인·분석 없음).**

앱이 직접 보내는 것이 없으면 신고 내용은 **SDK가 수집하는 것**이 전부다. SDK 제공사가 공개한
Play 데이터 보안 안내 페이지를 열어, **앱에 들어간 SDK 버전**에 해당하는 항목을 그대로 옮긴다.

- AdMob(Google Mobile Ads SDK): https://developers.google.com/admob/android/privacy/play-data-disclosure
- **[확인]** 이번 입력값(그 페이지 기준, 당시 SDK 버전):

| 데이터 유형 | 수집 | 공유 | 목적 |
|---|---|---|---|
| 대략적인 위치(IP 주소로 추정) | 예 | 예 | 광고 또는 마케팅 · 애널리틱스 · 사기 방지·보안·규정 준수 |
| 앱 상호작용 | 예 | 예 | 위와 같음 |
| 비정상 종료 기록·진단 | 예 | 예 | 위와 같음 |
| 기기 또는 기타 ID(광고 ID 포함) | 예 | 예 | 위와 같음 |

  암호화: 전송 중 암호화 「예」

- 위 표는 **이번에 그 페이지를 보고 넣은 값**이다. 페이지 내용과 SDK 버전이 바뀌므로
  **표를 옮겨 적지 말고 매번 페이지를 다시 열어 대조한다**
- 같은 앱의 `광고 ID` 선언(§2-2)과 어긋나지 않게 한다
- 동의 SDK(UMP)·업데이터 플러그인 등 **다른 라이브러리가 네트워크로 무엇을 보내는지**도 확인한다 (§1-8)

### 2-2. 앱 콘텐츠 — `주의 필요`

앱 설정을 마치면 `주의 필요` 항목이 따로 뜬다. 이번에는 3개였다.

| 항목 | 이번 답 | 이유 |
|---|---|---|
| 광고 ID | 예, 목적은 **광고 또는 마케팅** 하나 | `애널리틱스` 는 앱이 직접 쓰는 분석 도구(Firebase 등)를 뜻한다. 화면 설명을 읽고 판단한다 |
| 판매자 상태 | 예 (기본값) | 광고 수익이 있다. `아니요` 를 고르면 EU·영국 사용자에게 소비자 보호법이 적용되지 않는다고 안내된다 |
| 서비스 약관 URL | 비움 | 선택 항목이다. 개인정보처리방침 URL을 넣으면 안 된다 |

### 2-3. 스토어 설정

- 앱/게임, 카테고리, 태그, 연락처
- **태그는 콘솔이 주는 목록에서만 고른다(최대 5개).** 목록 전체를 받아 본 뒤
  **앱의 목적**을 기준으로 고른다. 기능(단어 암기)보다 목적(면접 준비)이 기준이다
- **[확인]** 기억에 있는 태그 이름이 목록에 없을 수 있다(예: "교육 > 학습")

### 2-4. 기본 스토어 등록정보

- `① 애셋 → ② 리뷰` 두 단계이고, `*` 가 붙은 섹션만 필수다
- 앱 이름 30자, 간단한 설명, 자세한 설명, 아이콘, 그래픽 이미지, 휴대전화 스크린샷
- 동영상·태블릿·데스크톱·XR은 선택이다

### 2-5. 프로덕션 버전 만들기

| 항목 | 메모 |
|---|---|
| 국가/지역 | 출시할 나라를 고른다 |
| App Bundle | 1-1·1-2를 점검한 AAB |
| 출시명 | 자유 형식 (예: `1.0.0 첫 출시`) |
| 출시 노트 | 언어 태그(`<ko-KR>`) 안에 쓴다 |

- 경고 "가독화(deobfuscation) 파일 없음"은 출시를 막지 않는다

### 2-6. 게시 개요 → 제출

- 변경사항이 한곳에 모인다. **각 행을 입력값과 대조한 뒤** 제출한다
- 빠른 검사가 도는 중에 제출해도 된다
- **관리형 게시**가 꺼져 있으면 심사를 통과하는 즉시 자동으로 공개된다
- **[이 계정]** 제출한 날 바로 통과했다. 게시 개요에서 `검토 중인 변경사항` 이
  사라지고 `최근 게시일` 이 표시되면 공개된 것이다. 스토어 주소
  `https://play.google.com/store/apps/details?id=<패키지>` 로 확인한다
- **[확인]** 게시 개요의 변경사항에 의도하지 않은 **폼 팩터**(예: PC용 Google Play Games)가
  「선택」 항목으로 함께 들어갈 수 있다. 원하지 않으면 제출 전에 각 행을 확인한다
- **[이 계정]** 두 번째 첫 출시는 심사에 **약 5일** 걸렸다. 같은 계정에서 비슷한 시기에 낸 다른
  첫 출시는 더 빨랐다. **이유는 알 수 없다.** 사용자가 이유를 물으면 추측(앱 종류, 권한, 광고 등)을
  사실처럼 말하지 말고 "알 수 없다"고 답한다. [문서 확인 필요] 구글이 안내하는 심사 기간
- **[확인]** 「앱 업데이트가 게시되었습니다」 알림은 **첫 출시에도** 온다. 이 문구만 보고 기존 앱의
  업데이트라고 읽지 않는다. 어느 앱인지 알림의 앱 이름·패키지로 확인한다
- **[확인]** 공개 직후에는 **Play 스토어 검색에 잡히지 않는다.** 확인이나 공유는
  스토어 주소(직접 링크)로 한다. 검색 노출은 시간이 지나야 된다 [문서 확인 필요: 걸리는 시간]

### 2-7. 공개 뒤 콘솔에 뜨는 권유

- **[확인]** 게임으로 등록하면 「게임에 Play 게임즈 서비스 추가」 같은 알림이 뜬다.
  **권유이지 필수가 아니다.** 출시·광고·업데이트에 영향이 없다
- 붙이기로 하면 따라오는 일: 네이티브 SDK 추가(**새 AAB와 심사**), 로그인 흐름,
  데이터 보안 신고 개정 [가설: 범위는 붙일 기능에 따라 다르다]
- 이런 알림은 사용자가 원할 때만 다룬다. 할 일 목록의 필수 항목과 구분해 안내한다

## 3. AdMob 연결 — 앱이 공개된 뒤에

광고가 있는 앱은 플레이 공개만으로 끝나지 않는다.

1. **[문서]** 비공개 Google Play 앱은 AdMob에 연결할 수 없다. 공개된 뒤에 진행한다
2. AdMob 앱 상태가 `검토 필요` 이면 **스토어 연결이 필요하다는 뜻이다.** 기다린다고
   바뀌지 않는다. `앱에 앱 스토어 추가` 에서 Google Play를 선택하고, 패키지 이름이나 스토어 URL로 검색한다
3. **[문서]** "앱 스토어에 앱을 방금 등록한 경우 앱이 연결되기까지 24~48시간이 걸릴 수
   있습니다. 경우에 따라 최대 일주일이 걸릴 수도 있습니다."
   **[확인]** 공개 당일에는 패키지 이름으로도, URL로도 검색되지 않았다.
   다음 날에도 `확인할 앱` → `설정 마침` → `Google Play로 연결` 에서
   "일치하는 Google Play 앱을 찾을 수 없음"이 나왔다. 이 상태에서는 `계속` 버튼이 회색으로 비활성화된다.
   **대화상자의 "새 AdMob 앱을 만드세요"는 고르지 않는다.** 새 앱을 만들면 앱 ID가 바뀐다.
   그러면 앱에 들어간 ID와 달라져서 다시 빌드하고 다시 심사를 받아야 한다. 패키지 이름이 맞으면 기다린다
4. **[확인]** 검색이 되면 `앱 스토어 선택 → 패키지 이름 확인 → 앱 인증` 3단계로 넘어간다.
   앱 인증에서는 **Play 등록정보의 개발자 웹사이트 도메인 루트에 있는 `app-ads.txt`**를 확인한다.
   - 이번 출시에서는 스토어 설정의 연락처에 웹사이트가 빠져 있었다. 그래서 "Google Play의 내 앱 등록정보에서
     개발자 웹사이트를 찾지 못했습니다"로 막혔다. 파일은 이미 올라가 있었다
   - 웹사이트를 넣고 저장하자 게시 개요에 제출할 변경사항이 생기지 않았다. 스토어 페이지에도 곧바로 반영됐다
   - 반영 여부 확인: 스토어 페이지 HTML에 그 도메인이 들어 있는지 본다. WebFetch는 페이지가 잘려서 이 부분이 안 보인다
   - `app-ads.txt` 한 줄 형식: `google.com, pub-<게시자번호>, DIRECT, f08c47fec0942fa0`
     (AdMob 앱 인증 화면에 나오는 줄을 그대로 쓴다)
   - 반영 직후 `업데이트 확인` 을 눌러도 바로 통과하지는 않았다. 1시간 뒤에도 마찬가지였다
   - **[문서]** "최근에 Google Play에서 개발자 웹사이트를 추가했거나 Google Play에서 앱 등록정보를 업데이트한 경우
     AdMob에서 이러한 변경사항을 감지하는 데 최대 24시간이 걸립니다."
     ([app-ads.txt 문제 해결](https://support.google.com/admob/answer/9776740?hl=ko))
     인증 화면에 나오는 "몇 분"은 파일 크롤링 시간이다. 스토어 변경 감지 시간과는 다르다
   - 기다리기 전 점검: `https/http` 둘 다 `200`(리다이렉트 허용), `text/plain`, 내용 일치, `robots.txt` 가 막지 않는지
   - **[확인]** 웹사이트가 처음부터 들어가 있어도, 스토어 연결은 곧바로 되고 앱 인증에서
     **「app-ads.txt 세부정보가 일치하지 않습니다」**가 날 수 있다. 점검 순서:
     (a) `https://<도메인>/app-ads.txt` 의 줄이 인증 화면의 줄과 **글자까지** 같은가
         (게시자 번호, 쉼표·공백, 대소문자)
     (b) Play 등록정보의 개발자 웹사이트가 **같은 도메인**인가.
         주소 끝의 `/` 나 하위 경로 차이는 상관없는 것으로 보였다 [가설]
     (c) 둘 다 맞으면 크롤링 시간차다. 저장 시각 + 24시간 뒤 `업데이트 확인`
   - **[이 계정]** 다른 앱에서도 인증까지 **하루 이상** 걸렸다(사용자 경험)
   - **[확인]** 웹사이트를 넣은 지 약 7시간 뒤에도 같은 오류가 났다. 24시간 안에 다시 눌렀을 때 인증이 완료됐다.
     기다릴 때는 "내일"이라고만 하지 말고 **저장한 시각 + 24시간**을 정확한 시각으로 알려 준다
   - **[확인]** 인증 완료 화면에 "동의 관리 플랫폼(CMP)"과 유럽 메시지 만들기가 나온다.
     이 단계는 **EEA·영국·스위스에 출시할 때만** 필요하다. 출시 국가가 그 밖이면 `완료` 를 누르고 넘어간다.
     메시지를 만들려면 앱에도 UMP SDK 동의 코드가 있어야 한다(`react-native-google-mobile-ads` 는 `AdsConsent`).
     그러면 재빌드와 재심사가 필요하다. 그래서 해당 국가에 출시할 계획이 있으면 **첫 빌드 전에** 넣는다
5. 연결하면 AdMob 검토가 진행된다(`준비 중`). **[문서]** "검토 중에는 앱의 광고 게재가 제한될 수도 있습니다."
6. `준비됨` 이 되면 광고가 정상적으로 게재된다

> 광고 확인까지 걸리는 시간 = 플레이 심사 + AdMob 연결(하루~일주일) + AdMob 검토(며칠).
> 광고를 빨리 확인해야 하면 이 기간을 처음부터 일정에 넣는다.

## 4. 이번에 틀린 것 — 반복하지 말 것

| 틀린 것 | 원인 | 대신 할 것 |
|---|---|---|
| 메뉴 경로를 기억으로 안내 | 화면을 보기 전에 답함 | 할 일 목록 항목을 누른다 |
| 없는 태그를 추천 | 목록을 보기 전에 추측함 | 목록 전체를 받아 보고 고른다 |
| 테스터 12명 요건이 걸린다고 안내 | 일반론을 이 계정에 적용함 | 대시보드를 보고 판단한다 |
| 광고 ID 목적에 애널리틱스 포함 | 화면 설명을 읽지 않음 | 선택지 설명을 읽고 답한다 |
| 스크린샷 비율 불일치 | 조건을 대조하지 않음 | 1-3 사전 점검 |
| 등록정보 문안의 사실 오류 | 코드와 대조하지 않음 | 1-5 사전 점검 |
| 16KB 오류로 업로드 실패 | 네이티브 빌드를 미리 검사하지 않음 | 1-2 사전 점검 |
| 버전 코드 재사용 오류 | 알고도 미룸 | 1-1. 교체 전에 먼저 올린다 |
| AdMob이 몇 시간이면 된다고 짐작 | 문서를 확인하지 않음 | 문서 기준 24~48시간, 최대 일주일 |
| 연락처에 웹사이트 누락 → AdMob 앱 인증 실패 | 연락처 입력값을 확인하지 않음 | 1-4. 광고 앱은 웹사이트와 `app-ads.txt` 를 미리 맞춘다 |
| 끝난 일을 다시 물음 | 받은 답을 기억하지 않음 | 확정된 답은 기록해 두고 다시 묻지 않는다 |
| 「기존 설치본이 덮어지지 않는다」고 앱 서명 경고 | 계획 문서의 「○○에 배포」를 사실로 봄 | 1-7. 실제로 설치된 배포본이 있는지 사용자에게 먼저 묻는다 |
| 첫 출시의 「업데이트가 게시되었습니다」를 기존 앱 업데이트로 읽음 | 알림 문구만 봄 | 2-6. 알림의 앱 이름·패키지로 확인한다 |
